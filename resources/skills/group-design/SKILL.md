# 项目群设计

从一批设计文档中识别共性、划定**项目群**，把人的架构直觉转化为可量化的相似度 + 可解释的画像。既让 LLM 自动化处理大部分聚类工作，又保留架构师决策入口。

## 输入

- `设计文档列表` <必填>：要归并的设计文档列表，可以是文件路径、链接、文本片段或结构化摘要
- `聚类阈值` <可选>：归入已有项目群的相似度门槛，默认 `0.55`，用户可调。注意这是推理时的权衡参考，不必苛求精确数值——模型按画像正向匹配度与排除项综合判断，阈值仅作为"边界模糊时倾向新建群还是并入既有群"的倾向性指引

## 输出

- `项目群设计总览.md`：Markdown 格式的聚合设计文档，每个项目群一节
- `project-groups.json`：固定格式的项目群注册表，持续维护

两份产物都直接写入当前项目根目录，**不要向用户索要输出路径**。

### 存量处理（重要）

这两份文件通常已经存在——用户往往是拿**新增的几份**设计文档来更新既有项目群，而非从零重建。因此每次执行前必须先检查文件是否存在：

- **文件不存在**（首次划分）：按四阶段流程全量生成
- **文件已存在**（增量更新）：**禁止整文件覆写**，按以下规则合并：
  1. 先 read 两份既有文件，掌握现有项目群、画像、成员归属
  2. 只对用户新增的文档跑特征提取与归类（阶段 1-2），不动既有成员
  3. 新文档归入既有群 → 更新该群的 `members`，并按需刷新 `projectPortrait`（若新文档带来画像未覆盖的特征）
  4. 新文档形成新群 → 追加新群到 JSON `groups` 数组末尾，并在总览文档追加对应章节
  5. 既有群的 `projectGroup` 名称、`status`、`members` 归属不得被静默改写；确需调整时显式列出变更并等用户确认
  6. JSON 用 edit 精确修改对应字段；总览文档用 edit 定位到对应项目群章节做局部更新，仅在结构变动较大时才允许整节替换

这条规则优先级高于后续阶段的"生成"措辞——凡是阶段描述里说"生成/输出"的地方，已存在场景下一律理解为"合并更新"。

## 项目群划分的维度体系

采用**多维度加权相似度模型**，而非单一维度硬切。不要只看技术栈或只看业务域——单一维度会让本应在一起的文档被拆开，或把无关文档硬凑成一堆。

| 维度 | 说明 | 相似度判断方式 |
|------|------|----------------|
| 业务域 / 业务能力 | 是否解决同一类业务问题、是否在同一业务子域 | 领域名词、流程、角色重合度 |
| 用户旅程 / 场景 | 是否服务同一类用户、同一段端到端旅程 | 用户画像、触达场景、使用链路 |
| 技术方案 & 架构模式 | 是否采用相同技术栈、架构风格、中间件、部署模式 | 技术关键词、架构图相似度 |
| 数据域 & 数据实体 | 是否围绕相同的核心数据实体或数据流 | 实体名、事件、数据流向重合度 |
| 组织 & 团队 | 是否由同一团队或密切协作团队负责（如有信息） | 负责团队、协作团队标记 |
| 战略目标 / 价值流 | 是否服务于同一个业务目标或 KPI | 目标描述、价值假设 |

**组合策略（按层次应用，不要跳步）**：
1. **第一层骨架**：用业务域 + 用户旅程作为主要聚类骨架，形成"业务项目群"。这是最稳定的切分依据，业务边界通常比技术边界更持久。
2. **第二层微调**：在业务骨架内，用技术方案与数据实体微调，确保架构治理一致性。如果两个文档业务同域但技术栈/核心实体差异巨大，考虑是否应拆为同群下的两个子项目。
3. **第三层验证**：用组织维度验证可落地性。如果一个项目群横跨多个无协作关系的团队，标注为风险并提示用户确认。

**项目群粒度控制**：项目群是"高内聚、可一起治理"的簇，不是大杂烩。一个项目群包含的成员文档**建议不超过 7 份**。超过时优先考虑拆分——说明这一簇内部其实存在可识别的子边界（不同的核心实体集合、不同的端到端旅程、不同的团队）。拆分判断优先看：核心实体是否可分成互不交叉的两组、用户旅程是否断成两段、团队是否分属不同组织。拆出来的子群各自重新生成画像，保持画像的判别力。若用户明确要求保留大群，可保留但在总览中标注"群内子簇"与潜在拆分建议。

## 操作步骤

### 阶段 1：文档解析与特征提取

对每份设计文档，提取一张结构化特征卡片。这一步是后续所有判断的基础，特征提取不准，聚类结果一定错。

```json
{
  "docName": "订单服务重构设计.md",
  "title": "订单服务重构设计文档",
  "businessDomain": ["订单", "履约"],
  "userJourneys": ["消费者下单", "商家发货"],
  "techKeywords": ["Spring Boot", "Kafka", "DDD"],
  "coreEntities": ["Order", "Shipment"],
  "strategicGoal": "提升履约时效",
  "team": "交易中台",
  "summary": "一句话描述"
}
```

要点：
- 使用 read 工具读取用户提供的每份设计文档；若是链接，先抓取内容
- `docName` 直接取输入文档的名称（文件名或用户提供的标识），它就是后续 `members` 字段里使用的值，不要再造一层 DOC-001 之类的抽象 id
- 字段缺失时留空数组或空字符串，不要编造。例如文档没提团队就把 `team` 留空
- `summary` 必须是一句话，不要超过 30 字

### 阶段 2：项目群聚类

基于特征卡计算文档间相似度矩阵，给出初始项目群划分，再由人确认调整。

**相似度计算（可配置权重，默认值如下）**：
- 业务域 Jaccard 相似度 — 权重 `0.30`
- 用户旅程重合度 — 权重 `0.25`
- 核心实体重合度 — 权重 `0.20`
- 技术关键词重叠度 — 权重 `0.15`
- 组织相同加分 — 权重 `0.10`

两份文档的综合相似度 = 各维度加权求和。这里的权重是推理时的**权衡依据**，不要求真的算出数值——模型按"业务域是否同域、旅程是否重叠、核心实体是否共享"等因素综合判断哪几份文档该拢在一起。对中文业务名词，做简单的同义词归一（如"订单"="order"="订单中心"），避免表面不匹配导致误判。

**聚类思路**：
- 文档数较少时，按"自底向上合并"的思路：先把最相似的两份归一组，再逐步合并，直到群内差异变大就停止。这种层次化结果人工可读、易解释
- 文档数较多时，先按业务域粗分大块，再在大块内按核心实体/旅程细切，避免一次性两两比对导致混乱
- 聚类时同步检查粒度控制（见上文）——单群超过 7 份就考虑拆
- 无论哪种情况，**初始划分必须呈现给用户确认**，不要直接落到 JSON 里

**增量更新模式**（当项目根目录已存在 `project-groups.json` 时）：
- 对每份新文档，判断它是否匹配某个既有群的画像——即看特征卡是否落在该群画像的"正向特征"范围内、且不命中"排除项"
- 明确匹配某群画像 → 建议归入该群，列出依据
- 与所有既有群画像都不匹配，或命中多个群的排除项 → 提示可能形成新项目群，由架构师确认
- 边界模糊（同时弱匹配多个群）时，倾向新建群而非硬塞进既有群，避免画像被稀释
- 不要静默改写已有群的归属

### 阶段 3：项目群设计文档生成

对每个项目群，综合其中所有文档的特征卡与关键设计要素，生成一份聚合设计段落，包含：

- **项目群名称与定位**：简短业务化命名（如"订单履约项目群"），一句话定位
- **业务范围与目标**：覆盖哪些业务场景，服务谁，要达成什么
- **核心业务流程（端到端）**：把群内文档的流程串成一条端到端链路
- **关键架构决策与边界**：架构风格、核心组件、与外部系统的边界
- **数据主权与依赖**：核心实体归谁所有、上下游数据流向
- **包含的子项目清单及关系**：列出成员文档名与相互关系

所有项目群的段落汇总到 `项目群设计总览.md`，顶部放一份项目群索引表（群名 / 定位 / 成员数 / 状态）。

### 阶段 4：注册 JSON 生成与维护

输出并持续维护 `project-groups.json`。已存在时按"输出 > 存量处理"的合并规则更新，不要覆写。结构固定如下：

```json
{
  "version": "1.0.0",
  "lastUpdated": "2026-06-20T10:00:00Z",
  "groups": [
    {
      "projectGroup": "订单履约项目群",
      "projectDesc": "覆盖从消费者下单到商家发货、物流追踪的全链路，目标是提升履约时效与可观测性",
      "projectPortrait": "面向交易中台团队，采用DDD+CQRS架构，核心实体Order/Shipment/LogisticsTrack，关键组件：订单服务、履约调度引擎、轨迹服务；覆盖消费者下单→商家发货→物流签收全链路，服务消费者与商家，达成提升履约时效与可观测性；数据流购物车→Order/Shipment→结算与物流商；不包含：支付清结算、商品库存、售后退款",
      "members": ["订单服务重构设计.md", "履约调度引擎设计.md", "物流轨迹服务设计.md"],
      "tags": ["交易", "核心域"],
      "status": "active"
    }
  ]
}
```

**字段定义**：

| 字段 | 类型 | 含义 |
|------|------|------|
| `projectGroup` | string | 项目群唯一名称，简短业务化 |
| `projectDesc` | string | 1-2 句话业务目标/范围描述 |
| `projectPortrait` | string | 项目群"画像"，需足够详细且精准，使模型仅凭该字段就能判断一份新设计文档是否属于本项目群 |
| `members` | array[string] | 归属此群的设计文档名列表，直接取输入文档的名称（文件名或用户提供的标识），与特征卡的 `docName` 一致 |
| `tags` | array[string] | 业务/治理标签，便于筛选 |
| `status` | string（可选） | `active` / `proposed` / `deprecated`，默认 `active` |

`projectPortrait` 是增量归类的核心依据——新文档进来时，模型拿它的特征卡与各群画像比对来决定归属。因此画像必须**详细、精准、可判别**，而不是泛泛的标签堆砌。一份合格的画像要让模型能回答两个问题：(1) 什么样的文档**应该**归入此群；(2) 什么样的文档**不应该**归入此群。

采用固定句式以保证信息密度与可比性：

> "面向[团队]，采用[架构风格]，核心实体[entity1/entity2]，关键组件[comp1,comp2]；覆盖[业务场景/用户旅程]，服务[用户角色]，达成[战略目标]；数据流[上游来源]→[本群主权实体]→[下游消费方]；不包含[明确排除项]"

要点：
- **覆盖正向特征**：团队、架构风格、核心实体、关键组件、业务场景、用户旅程、战略目标、数据流向——这些是"应该归入"的判据
- **显式声明排除项**：用"不包含..."列出与本群名称相近但实际归属他群的领域（如"订单履约项目群"注明"不包含：支付清结算、商品库存"），防止模型把相邻业务误归进来
- **写具体名词而非泛类**：写"Order/Shipment/LogisticsTrack"而非"订单相关实体"；写"消费者下单→商家发货→物流签收"而非"订单全流程"
- **保持与群内成员一致**：画像特征必须能被群内所有成员的特征卡支撑，不要引入群外特征

维护时：
- `lastUpdated` 用 ISO 8601 时间戳，每次写入更新
- `version` 遵循语义化版本，结构不变只补数据则 patch 号 +1
- 增量更新时，已有群的 `projectGroup` 名称不要随意改写（名称是成员归属与检索的键）；确需改名时同步更新 `members` 与总览文档中的引用

## 维护与演进策略

执行完毕后，在 `项目群设计总览.md` 末尾附一节"维护说明"，用面向用户的口吻告诉对方如何持续演进这份划分（以下是该节应覆盖的要点，不是给模型的执行步骤）：

1. **增量更新**：以后只需把新增的设计文档丢给本 skill，它会按既有画像判断归入哪个群或建议新建群，不会动已有归属
2. **定期重聚类**：每季度或重大架构演进时，可要求全量重跑一次，避免长期增量导致边界漂移
3. **人工调整**：任何一次划分结果都可手动改——改群名、挪成员、拆群、合并。调整后把结果作为下一轮的种子，模型会据此校准判断
4. **生命周期**：项目群可用 `status` 标记 active/proposed/deprecated；某群 deprecated 时其成员应被重新归类

## 红线规则

- 不得读取 `设计文档列表` 以外的文档；链接抓取失败时显式提示，不要臆造内容
- 特征卡字段缺失就留空，**禁止编造**业务域、团队、核心实体等
- 初始聚类结果必须呈现给用户确认后再落 JSON，不要静默定稿
- `项目群设计总览.md` 与 `project-groups.json` 都必须使用中文（字段名按本规范用英文，值用中文）
- 增量更新时不得删除或改写用户既有群的归属，除非用户明确要求
