# Codebase Sync — 项目代码变更后的文档树同步器

当项目源代码发生变更时，同步更新 `文档树路径` 下的文档树结构，
包括各级 `toc.md` 索引文件和 `spec-*.md` 规范文档。

本 skill 与 `openpowers-codebase-generator` 共享完全一致的文档生成规则和格式规范，
确保通过 `openpowers-codebase-sync` 创建或更新的文档与 `openpowers-codebase-generator` 生成的文档
在结构、命名、格式上完全一致，可被 `openpowers-codebase-explorer` 无缝查询。

## 输入参数

用户需提供以下信息（至少一项）：

1. **修改的文件路径列表**：被修改的源代码文件的相对路径列表（如 `src/electron/main/ipc/handler.ts`）
2. **修改的代码内容**：具体的代码变更内容或 diff
3. **修改的描述**：对变更的业务/功能描述（如"新增了文件读取的 IPC 处理器"）

如果用户未提供足够信息，使用 `AskUserQuestion` 工具询问确认。

## 技能配置

通过以下脚本查询技能配置：

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/config.py {当前项目路径} language experimental.codebases project.codebases
```

依次返回三个值：
  1. `language` — 输出语言。作为本次技能所有面向用户的回答和输出的语言，为 None 则默认使用中文。
  2. `experimental.codebases` — 技能开关。该值不是 `True` 时，**必须立即终止 openpowers-codebase-sync 技能**，不可继续做任何同步操作（这是用户的强制配置）。
  3. `project.codebases` — `文档树路径`，如果该值为 None，**必须立即终止 openpowers-codebase-sync 技能**。

## 前置概念

### 文档树结构

本 skill 维护的文档树结构与 `openpowers-codebase-generator` 完全一致：

```
{文档树路径}/
├── toc.md                          ← 总纲（总索引，≤500行）
├── {模块-a}/
│   ├── toc.md                      ← 模块索引（模块级索引，≤500行）
│   ├── {子模块-1}/
│   │   ├── toc.md                  ← 子模块索引（子模块级索引，≤500行）
│   │   ├── spec-xxx.md
│   │   └── spec-yyy.md
│   ├── {子模块-2}/
│   │   ├── toc.md
│   │   └── ...
│   └── spec-zzz.md                 ← 直接挂在模块下的spec
├── {模块-b}/
│   ├── toc.md
│   └── ...
```

## 参考资料

### Spec 文档生成规范

> **！！！重要！！！每次生成或更新 spec 文档之前，必须重新读取以下文件，严格遵循其规范。**
>
> **`references/SPEC-SYNC-GUIDE-zh.md`** — spec 文档同步/生成的标准规范，格式与 openpowers-codebase-generator 的 SPEC-GENERATION-GUIDE.md 完全一致。
>
> **不得跳过此步骤。**

### 索引文件同步规范

> **！！！重要！！！每次更新 toc.md 之前，必须重新读取以下文件。**
>
> **`references/TOC-SYNC-GUIDE-zh.md`** — toc.md 索引文件的同步更新规范，包含各级 toc.md 的格式模板和更新规则。

## 核心原则：严格增量，禁止扩大

**本次同步的唯一目标是处理用户输入的变更文件列表，不得扩大修改范围。**

具体约束：

1. **Spec 文档**：只创建或更新与变更文件直接对应的 spec，不得修改其他无关 spec。
2. **toc.md 索引**：只更新变更涉及的条目（行），不得重写整个 toc.md 文件。对于已存在的 toc.md，使用精确编辑（添加/修改/删除行），保留所有无关条目不变。
3. **模块/子模块结构**：除非变更文件明确属于新领域（需用户确认），否则不得创建新的模块或子模块。
4. **禁止全局梳理**：增量更新模式下不进行全局依赖分析、全局关系图重构等操作。仅在用户明确要求或首次初始化时执行。
5. **源文件读取范围**：只读取变更文件及其直接依赖（import 的模块），不向上追溯所有调用者。如果 spec 已存在且变更不影响其对外接口，甚至不需要读取依赖文件。

## 执行阶段

严格按以下阶段执行。不得跳过或合并阶段。

### 阶段一：判断文档树状态

1. 检查 `文档树路径` 目录是否存在以及是否为空（无 `toc.md` 文件）。
2. 根据检查结果进入不同分支：

#### 分支 A：文档树为空（首次初始化）

当 `文档树路径` 为空或不存在时，需要从零生成初始文档树。

**步骤**：

1. 读取项目关键模块和关键文档（比如 design.md、proposal.md、README.md），理解项目架构和模块划分。
2. 扫描主要代码目录结构，了解代码组织方式。
3. 综合架构设计和目录结构，确定模块划分。
   - **划分原则**：综合考虑架构层面（代码组织、职责划分）、业务层面（领域逻辑、功能边界）、目录结构以及整体视角（模块间的关系和依赖）。不要过于依赖目录结构。
   - **模块规模**：模块下子项（子模块 + 直接spec）总数 ≤ 30。子模块包含 5–40 个 spec。
4. **向用户展示模块规划，等待确认后再继续。** 展示内容包括：模块列表、每个模块的源码路径、预计子项数量。
5. 创建初始文档树骨架：
   - 创建总纲 `{文档树路径}/toc.md`（初始骨架版本，格式见阶段四）
   - 为每个模块创建目录和模块 `toc.md`（初始骨架版本）
   - 如果模块下有子模块，创建子模块目录和子模块 `toc.md`（初始骨架版本，格式模板见 `TOC-SYNC-GUIDE-zh.md` 第 2.3 节）
   - 对于每个有源码的 spec 位置，生成对应的 spec 文档（遵循 `references/SPEC-SYNC-GUIDE-zh.md`）
6. 所有 spec 生成完成后，进行**全面梳理**（与 openpowers-codebase-generator 5.8 一致）：
   - 重新阅读所有生成的 spec 文档，理解各模块、子模块之间的联系与依赖关系
   - 基于全局视角优化总纲 toc.md，补充：项目详细介绍、模块依赖关系图（分层 ASCII 图）、入口点说明
   - 如发现模块/子模块划分不合理，可适当调整（调整前需向用户说明原因）
7. 按阶段五的规则验证索引可追溯性，确保所有文档正确。

**初始总纲骨架格式**（与 openpowers-codebase-generator 阶段四格式一致）：

```markdown
# MyApp — 文档树

> 项目： `./my-app` 的项目文档。

MyApp 是一个基于 Web 的任务管理应用。

## 模块总览

### {模块A名称}

> {模块A详细简介：职责、覆盖的业务领域、关键功能}

涉及子模块/spec：（待补充）

索引：[模块A/toc.md](./module-a/toc.md)
```

**初始模块索引骨架格式**：

```markdown
# {模块可读名称}

> {模块详细简介：职责、覆盖的业务领域、关键功能}

## 模块关系图

（待补充）

## 子模块

（待补充）

## 直接 Spec 文档

（待补充）
```

#### 分支 B：文档树已存在（增量更新）

当 `文档树路径` 已有 `toc.md` 和模块目录时，执行增量更新。**严格遵循"核心原则"，只处理用户输入的变更文件列表，禁止扩大范围。**

**步骤**：

1. 读取用户提供的修改信息（文件路径、代码内容、变更描述）。**以用户提供的文件列表为唯一工作范围。**
2. 读取总纲 `{文档树路径}/toc.md`，确定变更涉及的模块（仅限包含变更文件的模块）。
3. 读取对应模块的 `toc.md`，确定变更涉及的子模块或直接 spec。
4. **范围自检**：输出本次操作涉及的所有文件清单，确认没有超出用户输入的变更范围。
5. 按阶段二的规则定位需要创建/更新的 spec 文档。
6. 按阶段三的规则更新 spec 文档。
7. 按阶段四的规则从下至上更新各级 toc.md。

### 阶段二：定位目标 Spec

根据变更的源文件路径和内容，确定需要创建或更新的 spec 文档：

1. **定位模块**：根据源文件路径（如 `src/electron/main/ipc/handler.ts`）和总纲 toc.md，确定所属模块。
2. **定位子模块/直接 spec**：根据模块 toc.md，确定变更涉及的子模块或直接 spec。
3. **确定操作类型**：
   - **新增 spec**：如果变更引入了新的业务逻辑/功能，且文档树中无对应 spec，需要创建新 spec。
   - **更新 spec**：如果变更修改了已有 spec 覆盖的源文件，需要更新对应 spec。
   - **删除 spec**：如果变更删除了某个功能/模块的源代码，需要删除对应 spec 并清理各级 toc.md 中的条目。
   - **新增子模块**：如果新增 spec 导致某模块下某领域的 spec 超过 5 个，可能需要创建新的子模块来组织。如果子模块 spec 超过 40 个，考虑拆分。
   - **删除子模块**：如果删除操作导致某子模块下的 spec 少于 5 个，应将剩余 spec 提升为模块下的直接 spec，删除子模块目录。

4. 输出内部日志：

```
[定位] 源文件：{文件路径}
[定位] 所属模块：{模块名}
[定位] 所属子模块：{子模块名} 或 直接spec
[定位] 操作类型：新增spec / 更新spec / 删除spec / 新增子模块 / 删除子模块
[定位] 目标spec：{spec路径}
```

### 阶段三：创建或更新 Spec 文档

> **！！！警告！！！** 每次创建或更新任何 spec 文档之前，必须重新读取 `references/SPEC-SYNC-GUIDE-zh.md`。
> 不得依赖记忆或之前的上下文。每次都要重新读取，严格遵循其中所有规范。
> 本步骤不可跳过。

**严格遵循以下规则**：

1. **重新读取源文件**：必须重新读取实际源文件，不能仅依赖用户提供的变更描述。**只读取变更文件本身，不扩大读取范围。**
2. **读取范围限制（增量模式）**：
   - 只读取本次变更涉及的源文件。
   - 如果 spec 已存在且变更不涉及对外接口（新增/修改/删除 export 的函数、类、类型），则不需要读取任何依赖文件，直接更新 spec 中对应的内容。
   - 如果变更涉及对外接口，可读取直接 import 的模块（仅一层），但**不得向上追溯调用者**。
3. **遵循规范格式**：严格按照 `references/SPEC-SYNC-GUIDE-zh.md` 的模板格式生成 spec 文档。
4. **核心代码判定**：审慎判定哪些代码是核心逻辑，避免将简单包装代码列入核心代码。
5. **局部更新 spec**：更新已有 spec 时，只修改与变更文件对应的内容段落（如函数说明、接口描述、核心代码片段），保留 spec 中其他不相关部分不变。**禁止重写整个 spec 文档。**
6. **写入 spec 文档**：创建或更新 spec 文件。
7. **删除 spec**：如果操作类型为"删除 spec"，直接删除 spec 文件即可，无需读取源文件。
8. **结构调整**：如果操作类型为"新增子模块"或"删除子模块"，按 `references/TOC-SYNC-GUIDE-zh.md` 第 3.3 节和第 3.5 节的规则执行目录创建/删除和文件移动。

每完成一个 spec，输出进度信息：`[spec] {模块}/{子模块}/spec-xxx.md — 完成`

### 阶段四：从下至上更新索引文件（toc.md）

**更新顺序：子模块 toc.md → 模块 toc.md → 总纲 toc.md**

严格自底向上更新，确保每一级索引的描述与下级内容保持一致。

**关键约束：对已有 toc.md 文件使用精确编辑（Edit 工具），只添加/修改/删除与变更相关的行，保留所有无关条目不变。禁止重写整个 toc.md 文件。**

> **！！！重要！！！更新每个 toc.md 前，必须先读取 `references/TOC-SYNC-GUIDE-zh.md`。**

#### 4.1 更新子模块 toc.md

如果变更涉及子模块下的 spec：

1. 读取当前子模块 `toc.md`。
2. 读取 `references/TOC-SYNC-GUIDE-zh.md` 中子模块 toc.md 的格式模板。
3. 更新 Spec 文档表格，添加/修改对应 spec 的条目（包含详细描述和源文件路径）。
4. 更新 Spec 关系图（如有必要）。
5. 确保描述足够详细以支持检索器导航。

**子模块 toc.md 格式**（与 openpowers-codebase-generator 5.4 格式一致）：

```markdown
# {子模块可读名称}

> {子模块详细简介：职责说明、覆盖范围}

## Spec 关系图

┌─────────────────────────┐
│       {Spec A 名称}              │
│       {覆盖的功能简述}            │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│       {Spec B 名称}              │
│       {覆盖的功能简述}            │
└─────────────────────────┘

## Spec 文档

| Spec | 描述 | 源文件 |
|------|------|--------|
| [spec-xxx.md](./spec-xxx.md) | {详细描述：覆盖的功能/接口说明} | `src/.../file.ts` |
| [spec-yyy.md](./spec-yyy.md) | {详细描述：覆盖的功能/接口说明} | `src/.../file2.ts` |
```

#### 4.2 更新模块 toc.md

如果子模块 toc.md 发生变化，或变更涉及模块下的直接 spec：

1. 读取当前模块 `toc.md`。
2. 读取 `references/TOC-SYNC-GUIDE-zh.md` 中模块 toc.md 的格式模板。
3. 更新子模块表格（子模块的描述、spec 数量）。
4. 更新直接 Spec 文档表格。
5. 更新模块关系图（如有必要）。
6. 确保描述足够详细以支持检索器导航。

**模块 toc.md 格式**（与 openpowers-codebase-generator 5.5 格式一致）：

```markdown
# {模块可读名称}

> {模块详细简介：职责、覆盖的业务领域、关键功能}

## 模块关系图

┌─────────────────────────┐
│     {子模块A / 直接spec名称}      │
│     {描述或职责简述}              │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│     {子模块B / 直接spec名称}      │
│     {描述或职责简述}              │
└─────────────────────────┘

## 子模块

| 子模块 | 描述 | Spec数 | 索引 |
|--------|------|--------|------|
| [submodule-1/](./submodule-1/) | {详细描述：职责说明、覆盖范围} | N个spec | [toc.md](./submodule-1/toc.md) |
| [submodule-2/](./submodule-2/) | {详细描述：职责说明、覆盖范围} | M个spec | [toc.md](./submodule-2/toc.md) |

## 直接 Spec 文档

| Spec | 描述 | 源文件 |
|------|------|--------|
| [spec-zzz.md](./spec-zzz.md) | {详细描述：覆盖的功能/接口说明} | `src/.../file.ts` |
```

#### 4.3 更新总纲 toc.md

如果模块 toc.md 发生变化：

1. 读取当前总纲 `toc.md`。
2. 读取 `references/TOC-SYNC-GUIDE-zh.md` 中总纲 toc.md 的格式模板。
3. 更新对应模块的条目，确保包含：
   - 模块的详细简介（职责、覆盖的业务领域、关键功能）
   - 子模块的详细简介（职责说明、覆盖范围）及 spec 数量
   - 直接 spec 的详细简介（覆盖的功能/接口说明）
   - 模块索引文件路径链接
4. 确保描述足够详细以支持检索器导航。

**总纲 toc.md 格式**（与 openpowers-codebase-generator 5.6 格式一致）：

```markdown
# MyApp — 文档树

> 自动为 `./my-app` 生成的项目文档。

## 模块总览

### {模块A名称}

> {模块A详细简介：职责、覆盖的业务领域、关键功能}

- **子模块**
  - `{子模块1}` — {子模块1详细简介：职责说明、覆盖范围}（N个spec）
  - `{子模块2}` — {子模块2详细简介：职责说明、覆盖范围}（M个spec）
- **直接spec**
  - `spec-xxx.md` — {spec详细简介：覆盖的功能/接口说明}
  - `spec-yyy.md` — {spec详细简介：覆盖的功能/接口说明}
- **索引文件**：[模块A/toc.md](./module-a/toc.md)

### {模块B名称}

> {模块B详细简介：职责、覆盖的业务领域、关键功能}

- **子模块**
  - `{子模块3}` — {子模块3详细简介：职责说明、覆盖范围}（K个spec）
- **直接spec**
  - `spec-zzz.md` — {spec详细简介：覆盖的功能/接口说明}
- **索引文件**：[模块B/toc.md](./module-b/toc.md)
```

每完成一个 toc.md 的更新，输出进度信息：`[toc] {路径} — 已更新`

### 阶段五：验证索引可追溯性（仅限变更范围）

更新完成后，**仅对本次变更涉及的条目**进行索引可追溯性验证。不得对整个文档树做全面检查。

1. 验证本次更新/创建的 spec 文档在对应子模块/模块 toc.md 中有对应条目。
2. 验证子模块 toc.md 中本次变更的条目在模块 toc.md 中有反映。
3. 验证模块 toc.md 中本次变更的条目在总纲 toc.md 中有反映。
4. 验证本次变更涉及的 toc.md 条目中的链接路径是否正确。
5. 验证本次更新的 spec 文档的源文件路径是否真实匹配。

每完成一个验证，输出：`[check] {路径} — 通过`

如发现问题，立即修正。

## 关键规则

1. **与 openpowers-codebase-generator 规则完全一致。** 本 skill 生成的所有 toc.md 和 spec 文档，在格式、结构、命名、描述规范上必须与 openpowers-codebase-generator 完全一致。这是最核心的要求。
2. **禁止使用脚本**（读取技能配置的 `config.py` 除外）。所有分析和生成通过直接读取源文件完成。不得编写或执行辅助脚本。
3. **自底向上更新。** 索引文件的更新顺序必须是：子模块 toc.md → 模块 toc.md → 总纲 toc.md。先更新下级内容，再更新上级索引。
4. **索引文件 ≤ 500行。** 所有 toc.md 文件（总纲、模块索引、子模块索引）必须保持精简。它们是索引，不是详细文档。
5. **每个 spec 必须重新扫描源文件（但仅限变更文件）。** 创建或更新 spec 时，必须重新读取实际源文件。但只读取变更文件本身，不得扩大扫描范围到无关文件。
6. **核心代码需审慎判定。** 不是所有代码都值得列入 spec 文档。应优先选取真正体现核心逻辑、关键算法、重要接口实现的代码。
7. **spec 文档必须详实专业。** 每个 spec 文档是对一个或数个相关源文件的完整技术规格说明。必须对每个重要功能/接口/方法进行详细解读。
8. **描述必须支持检索器导航。** 总纲 → 模块索引 → 子模块索引 → spec 文档的路径必须顺畅。用户给出一个查询描述，应能通过逐级索引顺利定位到正确的 spec。
9. **每次生成/更新 spec 前必须重新读取规范文件。** `references/SPEC-SYNC-GUIDE-zh.md` 是 spec 文档生成的标准规范。每次处理任何 spec 文档之前都要重新读取该文件。
10. **每次更新 toc.md 前必须读取索引规范。** `references/TOC-SYNC-GUIDE-zh.md` 是 toc.md 更新的标准规范。
11. **模块/子模块规模。** 一个模块的子项（子模块 + 直接spec）总数 ≤ 30。一个子模块包含 5–40 个 spec 文档。如果某个领域少于 5 个 spec，应作为模块下的直接 spec，而非子模块。
12. **综合判断，不要过于依赖目录结构。** 划分模块和子模块时，应综合考虑架构层面、业务层面、目录结构及整体视角。目录结构只是参考之一。
13. **进度报告。** 完成每个条目时，输出带 `[spec]`、`[toc]`、`[check]` 前缀的进度信息。
14. **跳过测试文件。** 凡是匹配 `*.test.ts`、`*.test.js`、`*.spec.ts`、`*.spec.js`、`__tests__/**`、`**/test/**`、`**/tests/**` 等测试相关的文件，一律跳过，不生成 spec 文档，不纳入文档树。
