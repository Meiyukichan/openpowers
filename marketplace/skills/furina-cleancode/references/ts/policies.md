# 策略

## Consistency

对于本规范未明确解决的所有风格问题，请执行与同一文件中已有代码相同的操作（"保持一致"）。如果这不能解决问题，考虑模拟同一目录中的其他文件。

新文件**必须**使用 Google 风格，无论同一包中其他文件的风格选择如何。向不是 Google 风格的文件添加新代码时，建议先重新格式化现有代码。如果不进行此重新格式化，新代码**应该**尽可能与同一文件中的现有代码保持一致，但**禁止**违反风格指南。

### Reformatting existing code

你偶尔会遇到代码库中格式不正确的文件。这些可能来自收购，或者可能在 Google 风格对某些问题采取立场之前编写的，或者可能出于任何其他原因使用非 Google 风格。

更新现有代码的样式时，请遵循以下指南：

1. 不需要更改所有现有代码以符合当前风格指南。重新格式化现有代码是代码变动和一致性之间的权衡。风格规则随时间演变，这些保持合规性的调整会产生不必要的变动。但是，如果对文件进行了重大更改，则该文件应该符合 Google 风格。
2. 注意不要让机会主义风格修复混淆 CL 的焦点。如果你发现自己做了很多与 CL 中心焦点无关的样式更改，将这些更改提升到单独的 CL。

## Deprecation

使用 `@deprecated` JSDoc 注解标记已弃用的方法、类或接口。弃用注释必须包含简单的、清晰的指导，说明人们如何修复他们的调用点。

## Generated code: mostly exempt

构建过程生成的源代码不需要符合 Google 风格。但是，任何将从手写源代码引用的生成标识符必须遵循命名要求。作为一个特殊的异常，此类标识符允许包含下划线，这有助于避免与手写标识符冲突。

### Style guide goals

一般来说，工程师通常最了解他们的代码需要什么，所以如果有多个选项且选择取决于情况，我们应该让决策在本地做出。所以默认答案应该是"省略它"。

以下几点是例外，是我们有一些全局规则的原因。根据以下内容评估你的风格指南提案：

1. **代码应该避免已知会导致问题的模式，特别是对语言新手来说。**
2. **跨项目的代码应该在无关的变体中保持一致。** 当有两种在表面上看似等效的选项时，我们应该考虑选择一个，只是为了不要无意义地分歧演化，并避免在代码审查中无意义的争论。例如：名称的大小写风格、`x as T` 语法与等效的 `<T>x` 语法（禁止）、`Array<[number, number]>` 与 `[number, number][]`。
3. **代码应该长期可维护。** 代码通常比原始作者工作时间更长，TypeScript 团队必须让 Google 的所有代码在未来继续工作。例如：我们使用软件自动化代码更改，因此代码是自动格式化的，以便软件易于满足空白规则。我们要求一组单一的编译器标志，以便给定的 TS 库可以假设一组特定的标志编写，用户始终可以安全地使用共享库。代码必须导入它使用的库（"严格依赖"），以便对依赖项的重构不会改变其用户的依赖项。我们要求用户编写测试。没有测试，我们就无法对我们对语言所做的更改是否破坏用户有信心。
4. **代码审查者应该专注于提高代码质量，而不是强制执行任意规则。** 如果你的规则可以作为自动化检查实现，那通常是一个好迹象。这也支持原则 3。如果它真的不重要——如果它是语言的模糊角落或者只是避免了一个不太可能发生的 bug——可能值得省略。
