# Codebase Sync — Codebase Synchronizer After Code Changes

When project source code changes occur, sync updates to the Codebase structure under `{doc-tree-path}`,
including all levels of `toc.md` index files and `spec-*.md` specification documents.

This skill shares identical document generation rules and format specifications with `openpowers-codebase-generator`,
ensuring that documents created or updated via `openpowers-codebase-sync` are fully consistent
in structure, naming, and format with those generated by `openpowers-codebase-generator`,
and can be seamlessly queried by `openpowers-codebase-explorer`.

## Input Parameters

The user must provide at least one of the following:

1. **Modified file paths**: Relative paths of changed source files (e.g., `src/electron/main/ipc/handler.ts`)
2. **Modified code content**: Specific code changes or diff
3. **Change description**: Business/functional description of the changes (e.g., "Added IPC handler for file reading")

If the user does not provide sufficient information, use the `AskUserQuestion` tool to confirm.

## Skill Configuration

Query skill configuration via the following script:

```bash
openpowers config show language project.codebases.enable project.codebases.path
```

Returns three values in order:

1. `language` — Output language. Used for all user-facing responses and outputs in this skill invocation. If None, defaults to Chinese.
2. `project.codebases.enable` — Skill toggle. When this value is not `true`, **you must immediately terminate the openpowers-codebase-sync skill** and must not proceed with any sync operations (this is a mandatory user configuration).
3. `project.codebases.path` — `Codebase path`. If this value is None, **you must immediately terminate the openpowers-codebase-sync skill**.

## Prerequisites

### Codebase Structure

The Codebase structure maintained by this skill is fully consistent with `openpowers-codebase-generator`:

```
{doc-tree-path}/
├── toc.md                          ← Root index (total index, ≤500 lines)
├── {module-a}/
│   ├── toc.md                      ← Module index (module-level index, ≤500 lines)
│   ├── {submodule-1}/
│   │   ├── toc.md                  ← Submodule index (submodule-level index, ≤500 lines)
│   │   ├── spec-xxx.md
│   │   └── spec-yyy.md
│   ├── {submodule-2}/
│   │   ├── toc.md
│   │   └── ...
│   └── spec-zzz.md                 ← Direct spec under module
├── {module-b}/
│   ├── toc.md
│   └── ...
```

### Codebase Path

The Codebase root directory is: `{doc-tree-path}` (obtained from the skill configuration above).

### Index File Sync Guidelines

> **!!! IMPORTANT !!! Before updating any toc.md, you must re-read the following file.**
>
> **`references/TOC-SYNC-GUIDE.md`** — Sync update specification for toc.md index files, including format templates and update rules for all levels of toc.md.

## Core Principle: Strictly Incremental, No Scope Expansion

**The sole purpose of this sync is to process the changed file list provided by the user. Do not expand the scope of modifications.**

Specific constraints:

1. **Spec Documents**: Only create or update specs directly corresponding to changed files. Do not modify other unrelated specs.
2. **toc.md Indices**: Only update the entries (lines) involved in the changes. Do not rewrite the entire toc.md file. For existing toc.md files, use precise edits (add/modify/delete lines), preserving all unrelated entries unchanged.
3. **Module/Submodule Structure**: Do not create new modules or submodules unless the changed files clearly belong to a new domain (requires user confirmation).
4. **No Global Analysis**: In incremental update mode, do not perform global dependency analysis, global relationship diagram reconstruction, etc. Only perform these when explicitly requested by the user or during initial initialization.
5. **Source File Reading Scope**: Only read changed files and their direct dependencies (imported modules). Do not trace upward to all callers. If a spec already exists and the change does not affect its external interface, you may not even need to read dependency files.

## Execution Phases

Execute strictly in the following phases. Do not skip or merge phases.

### Phase 1: Determine Codebase State

1. Check whether `{doc-tree-path}` directory exists and whether it is empty (no `toc.md` file).
2. Branch based on the check result:

#### Branch A: Codebase is Empty (First-time Initialization)

When `{doc-tree-path}` is empty or does not exist, generate the initial Codebase from scratch.

**Steps**:

1. Read key modules and key documents of the project (such as design.md, proposal.md, README.md) to understand project architecture and module division.
2. Scan the main code directory structure to understand code organization.
3. Combine architectural design and directory structure to determine module division.
   - **Division Principles**: Consider architecture (code organization, responsibility division), business (domain logic, functional boundaries), directory structure, and holistic perspective (inter-module relationships and dependencies). Do not over-rely on directory structure.
   - **Module Scale**: Total sub-items under a module (submodules + direct specs) ≤ 30. Submodules contain 5-40 specs.
4. **Present the module plan to the user and wait for confirmation before continuing.** Include: module list, source paths for each module, estimated sub-item count.
5. Create the initial Codebase skeleton:
   - Create root `{doc-tree-path}/toc.md` (initial skeleton version, format per Phase 4)
   - Create directories and module `toc.md` for each module (initial skeleton version)
   - If a module has submodules, create submodule directories and submodule `toc.md` (initial skeleton version, format template in `TOC-SYNC-GUIDE.md` section 2.3)
   - For each spec position with source code, generate the corresponding spec document (following `references/SPEC-SYNC-GUIDE.md`)
6. After all specs are generated, perform **comprehensive review** (consistent with openpowers-codebase-generator 5.8):
   - Re-read all generated spec documents to understand relationships and dependencies between modules and submodules
   - Optimize the root toc.md from a global perspective, adding: detailed project introduction, module dependency diagram (layered ASCII diagram), entry point descriptions
   - If module/submodule division is found unreasonable, adjust appropriately (explain reasons to the user before adjusting)
7. Verify index traceability per Phase 5 rules to ensure all documents are correct.

**Initial Root Skeleton Format** (consistent with openpowers-codebase-generator Phase 4 format):

```markdown
# MyApp — Codebase

> Project: documentation for `./my-app`.

MyApp is a web-based task management application.

## Module Overview

### {Module A Name}

> {Detailed module A introduction: responsibilities, business domains covered, key features}

Involved submodules/specs: (to be added)

Index: [ModuleA/toc.md](./module-a/toc.md)
```

**Initial Module Index Skeleton Format**:

```markdown
# {Module Readable Name}

> {Detailed module introduction: responsibilities, business domains covered, key features}

## Module Relationship Diagram

(to be added)

## Submodules

(to be added)

## Direct Spec Documents

(to be added)
```

#### Branch B: Codebase Already Exists (Incremental Update)

When `{doc-tree-path}` already has `toc.md` and module directories, perform incremental update. **Strictly follow the "Core Principle", only process the changed file list provided by the user. Do not expand scope.**

**Steps**:

1. Read the modification information provided by the user (file paths, code content, change descriptions). **Use the user's file list as the sole work scope.**
2. Read the root `{doc-tree-path}/toc.md` to determine which modules are affected by the changes (only modules containing changed files).
3. Read the corresponding module `toc.md` to determine which submodules or direct specs are affected.
4. **Scope Self-check**: Output a list of all files involved in this operation, confirming they do not exceed the change scope provided by the user.
5. Locate spec documents to create/update per Phase 2 rules.
6. Update spec documents per Phase 3 rules.
7. Update toc.md files bottom-up per Phase 4 rules.

### Phase 2: Locate Target Spec

Based on the changed source file paths and content, determine which spec documents need to be created or updated:

1. **Locate Module**: Based on the source file path (e.g., `src/electron/main/ipc/handler.ts`) and root toc.md, determine the owning module.
2. **Locate Submodule/Direct Spec**: Based on the module toc.md, determine the affected submodule or direct spec.
3. **Determine Operation Type**:
   - **Add Spec**: If the change introduces new business logic/functionality with no corresponding spec in the Codebase, create a new spec.
   - **Update Spec**: If the change modifies source files covered by an existing spec, update the corresponding spec.
   - **Delete Spec**: If the change removes source code for a feature/module, delete the corresponding spec and clean up entries in all levels of toc.md.
   - **Add Submodule**: If adding specs causes a domain within a module to exceed 5 specs, consider creating a new submodule to organize them. If a submodule exceeds 40 specs, consider splitting it.
   - **Delete Submodule**: If deletion causes a submodule to have fewer than 5 specs, promote remaining specs to direct specs under the module and delete the submodule directory.

4. Output internal log:

```
[locate] Source file: {file path}
[locate] Owning module: {module name}
[locate] Owning submodule: {submodule name} or direct spec
[locate] Operation type: add-spec / update-spec / delete-spec / add-submodule / delete-submodule
[locate] Target spec: {spec path}
```

### Phase 3: Create or Update Spec Document

> **!!! WARNING !!!** Before creating or updating any spec document, you must re-read `references/SPEC-SYNC-GUIDE.md`.
> Do not rely on memory or previous context. Re-read it every time and strictly follow all its specifications.
> This step cannot be skipped.

**Strictly follow these rules**:

1. **Re-read Source Files**: Must re-read actual source files, not just rely on change descriptions from the user. **Only read changed files themselves, do not expand reading scope.**
2. **Reading Scope Limit (Incremental Mode)**:
   - Only read source files involved in this change.
   - If a spec already exists and the change does not affect external interfaces (new/modified/deleted exported functions, classes, types), no need to read any dependency files — directly update the corresponding content in the spec.
   - If the change affects external interfaces, you may read directly imported modules (one level only), but **do not trace upward to callers**.
3. **Follow Specification Format**: Generate spec documents strictly according to the template format in `references/SPEC-SYNC-GUIDE.md`.
4. **Core Code Determination**: Carefully judge which code is core logic, avoid including simple wrapper code as core code.
5. **Partial Spec Updates**: When updating an existing spec, only modify content sections corresponding to changed files (e.g., function descriptions, interface descriptions, core code snippets). Preserve all other unrelated parts of the spec unchanged. **Do not rewrite the entire spec document.**
6. **Write Spec Document**: Create or update the spec file.
7. **Delete Spec**: If the operation type is "delete spec", delete the spec file directly. No need to read source files.
8. **Structural Changes**: If the operation type is "add submodule" or "delete submodule", perform the directory creation/deletion and file moves as described in `references/TOC-SYNC-GUIDE.md` sections 3.3 and 3.5.

For each completed spec, output progress: `[spec] {module}/{submodule}/spec-xxx.md — done`

### Phase 4: Bottom-Up Index File Update (toc.md)

**Update Order: Submodule toc.md → Module toc.md → Root toc.md**

Strictly bottom-up update, ensuring each level's index descriptions are consistent with lower-level content.

**Key Constraint: For existing toc.md files, use precise edits (Edit tool), only add/modify/delete lines related to changes. Preserve all unrelated entries unchanged. Do not rewrite the entire toc.md file.**

> **!!! IMPORTANT !!! Before updating each toc.md, you must first read `references/TOC-SYNC-GUIDE.md`.**

#### 4.1 Update Submodule toc.md

If changes involve specs under a submodule:

1. Read current submodule `toc.md`.
2. Read the submodule toc.md format template from `references/TOC-SYNC-GUIDE.md`.
3. Update the Spec Documents table, add/modify corresponding spec entries (including detailed descriptions and source file paths).
4. Update the Spec Relationship Diagram (if necessary).
5. Ensure descriptions are detailed enough to support retriever navigation.

**Submodule toc.md Format** (consistent with openpowers-codebase-generator 5.4 format):

```markdown
# {Submodule Readable Name}

> {Detailed submodule introduction: responsibility description, coverage scope}

## Spec Relationship Diagram

┌─────────────────────────┐
│ {Spec A Name} │
│ {Feature summary covered} │
└───────────┬─────────────┘
│
▼
┌─────────────────────────┐
│ {Spec B Name} │
│ {Feature summary covered} │
└─────────────────────────┘

## Spec Documents

| Spec                         | Description                                         | Source File        |
| ---------------------------- | --------------------------------------------------- | ------------------ |
| [spec-xxx.md](./spec-xxx.md) | {Detailed description: features/interfaces covered} | `src/.../file.ts`  |
| [spec-yyy.md](./spec-yyy.md) | {Detailed description: features/interfaces covered} | `src/.../file2.ts` |
```

#### 4.2 Update Module toc.md

If submodule toc.md changes, or changes involve direct specs under the module:

1. Read current module `toc.md`.
2. Read the module toc.md format template from `references/TOC-SYNC-GUIDE.md`.
3. Update the submodule table (submodule descriptions, spec counts).
4. Update the Direct Spec Documents table.
5. Update the Module Relationship Diagram (if necessary).
6. Ensure descriptions are detailed enough to support retriever navigation.

**Module toc.md Format** (consistent with openpowers-codebase-generator 5.5 format):

```markdown
# {Module Readable Name}

> {Detailed module introduction: responsibilities, business domains covered, key features}

## Module Relationship Diagram

┌─────────────────────────┐
│ {SubmoduleA / Direct spec name} │
│ {Description or responsibility} │
└───────────┬─────────────┘
│
▼
┌─────────────────────────┐
│ {SubmoduleB / Direct spec name} │
│ {Description or responsibility} │
└─────────────────────────┘

## Submodules

| Submodule                      | Description                                      | Spec Count | Index                          |
| ------------------------------ | ------------------------------------------------ | ---------- | ------------------------------ |
| [submodule-1/](./submodule-1/) | {Detailed description: responsibility, coverage} | N specs    | [toc.md](./submodule-1/toc.md) |
| [submodule-2/](./submodule-2/) | {Detailed description: responsibility, coverage} | M specs    | [toc.md](./submodule-2/toc.md) |

## Direct Spec Documents

| Spec                         | Description                                         | Source File       |
| ---------------------------- | --------------------------------------------------- | ----------------- |
| [spec-zzz.md](./spec-zzz.md) | {Detailed description: features/interfaces covered} | `src/.../file.ts` |
```

#### 4.3 Update Root toc.md

If module toc.md changes:

1. Read current root `toc.md`.
2. Read the root toc.md format template from `references/TOC-SYNC-GUIDE.md`.
3. Update the corresponding module entry, ensuring inclusion of:
   - Detailed module introduction (responsibilities, business domains covered, key features)
   - Detailed submodule introductions (responsibility descriptions, coverage) and spec counts
   - Detailed direct spec introductions (features/interfaces covered)
   - Module index file path link
4. Ensure descriptions are detailed enough to support retriever navigation.

**Root toc.md Format** (consistent with openpowers-codebase-generator 5.6 format):

```markdown
# MyApp — Codebase

> Automatically generated documentation for `./my-app`.

## Module Overview

### {Module A Name}

> {Detailed module A introduction: responsibilities, business domains covered, key features}

- **Submodules**
  - `{submodule-1}` — {Detailed submodule 1 introduction: responsibility, coverage} (N specs)
  - `{submodule-2}` — {Detailed submodule 2 introduction: responsibility, coverage} (M specs)
- **Direct Specs**
  - `spec-xxx.md` — {Detailed spec introduction: features/interfaces covered}
  - `spec-yyy.md` — {Detailed spec introduction: features/interfaces covered}
- **Index File**: [ModuleA/toc.md](./module-a/toc.md)

### {Module B Name}

> {Detailed module B introduction: responsibilities, business domains covered, key features}

- **Submodules**
  - `{submodule-3}` — {Detailed submodule 3 introduction: responsibility, coverage} (K specs)
- **Direct Specs**
  - `spec-zzz.md` — {Detailed spec introduction: features/interfaces covered}
- **Index File**: [ModuleB/toc.md](./module-b/toc.md)
```

For each completed toc.md update, output progress: `[toc] {path} — updated`

### Phase 5: Verify Index Traceability (Only for Changed Scope)

After updates complete, verify index traceability **only for entries involved in this change**. Do not perform a comprehensive check of the entire Codebase.

1. Verify that spec documents created/updated in this session have corresponding entries in the submodule/module toc.md.
2. Verify that entries changed in this session in submodule toc.md are reflected in the module toc.md.
3. Verify that entries changed in this session in module toc.md are reflected in the root toc.md.
4. Verify that link paths in toc.md entries involved in this change are correct.
5. Verify that source file paths in updated spec documents actually match.

For each completed verification, output: `[check] {path} — passed`

If problems are found, fix them immediately.

## Key Rules

1. **Fully consistent with openpowers-codebase-generator rules.** All toc.md and spec documents generated by this skill must be fully consistent with openpowers-codebase-generator in format, structure, naming, and description specifications. This is the most core requirement.
2. **No scripts allowed** (except `config.py` for reading skill configuration). All analysis and generation is done by directly reading source files. Do not write or execute helper scripts.
3. **Bottom-up updates.** Index file update order must be: submodule toc.md → module toc.md → root toc.md. Update lower-level content first, then update upper-level indices.
4. **Index files ≤ 500 lines.** All toc.md files (root, module index, submodule index) must remain concise. They are indices, not detailed documents.
5. **Each spec must re-scan source files (but only changed files).** When creating or updating specs, must re-read actual source files. But only read changed files themselves, do not expand scanning scope to unrelated files.
6. **Core code must be carefully determined.** Not all code deserves inclusion in spec documents. Prioritize code that truly embodies core logic, key algorithms, and important interface implementations.
7. **Spec documents must be detailed and professional.** Each spec document is a complete technical specification for one or more related source files. Each important function/interface/method must be thoroughly detailed.
8. **Descriptions must support retriever navigation.** The path root → module index → submodule index → spec document must be smooth. When a user provides a query description, they should be able to locate the correct spec through progressive indices.
9. **Must re-read specification file before each spec generation/update.** `references/SPEC-SYNC-GUIDE.md` is the standard specification for spec document generation. Re-read this file before processing any spec document.
10. **Must read index specification before each toc.md update.** `references/TOC-SYNC-GUIDE.md` is the standard specification for toc.md updates.
11. **Module/submodule scale.** Total sub-items under a module (submodules + direct specs) ≤ 30. A submodule contains 5-40 spec documents. If a domain has fewer than 5 specs, it should be a direct spec under the module, not a submodule.
12. **Comprehensive judgment, do not over-rely on directory structure.** When dividing modules and submodules, comprehensively consider architecture, business, directory structure, and holistic perspective. Directory structure is only one reference.
13. **Progress reporting.** When completing each item, output progress with `[spec]`, `[toc]`, `[check]` prefixes.
14. **Skip test files.** Any files matching `*.test.ts`, `*.test.js`, `*.spec.ts`, `*.spec.js`, `__tests__/**`, `**/test/**`, `**/tests/**` and similar test-related patterns are skipped entirely, no spec documents generated, not included in the Codebase.
