# Openpowers Codebase Explorer — Document-tree-based Code Feature Query Tool

Navigate through the structured document tree generated by openpowers-codebase-generator, locating relevant spec documents and source code implementations based on user-provided business/feature descriptions.

## Language Adaptation

Query the plugin's required output language using the following script:

```bash
openpowers config show language
```

Use the language returned by the script as the default language for all user-facing responses and outputs in this skill. If the script returns no output or fails, fall back to Chinese.

## Input Parameters

The user must provide the following two parameters:

1. **Document tree path**: The root directory of the document tree generated by openpowers-codebase-generator (containing `toc.md` as the master index).
2. **Query description**: A brief description of the business, feature, or code module to find, such as "tool registration module" or "MCP protocol implementation".

If the user does not explicitly specify them, use the AskUserQuestion tool to confirm.

## Prerequisites

This skill depends on a document tree already generated by openpowers-codebase-generator. The document tree structure is as follows:

```
{document tree path}/
├── toc.md                          ← Master index (entry point)
├── {module-a}/
│   ├── toc.md                      ← Module index
│   ├── {submodule-1}/
│   │   ├── toc.md                  ← Submodule index
│   │   ├── spec-xxx.md
│   │   └── spec-yyy.md
│   └── spec-zzz.md
├── {module-b}/
│   ├── toc.md
│   └── ...
```

Each level's toc.md in the document tree contains detailed feature descriptions for hierarchical navigation:

- **Master index toc.md**: Lists detailed introductions of all modules, submodules, and direct specs
- **Module toc.md**: Lists detailed introductions of all submodules and direct specs under that module
- **Submodule toc.md**: Lists detailed introductions of all specs under that submodule

## Execution Phases

Execute strictly in the following order.

### Path Conversion Rules

All links in toc.md are relative paths (e.g., `./module-a/toc.md`, `./submodule-1/spec-xxx.md`) and must be converted to absolute paths before reading.

- Links in the master index `toc.md`: relative to `{document tree path}/`
- Links in a module `toc.md`: relative to `{document tree path}/{module}/`
- Links in a submodule `toc.md`: relative to `{document tree path}/{module}/{submodule}/`

Before reading any link in a toc.md, always convert it to an absolute path first. For example, `./module-a/toc.md` in the master index → `{document tree path}/module-a/toc.md`.

### Results List

Starting from Phase 1, maintain a **results list** `matched_specs`. All found specs are uniformly appended to this list, and Phase 4 outputs based on it. **`matched_specs` holds at most 4 specs**; when exceeded, prioritize the ones most relevant to the query description.

```
matched_specs = [
  {
    "spec_path": "path to the spec document",
    "match_source": "master-index-direct-hit | module-direct-spec | submodule-spec",
    "match_reason": "reason for the match"
  },
  ...
]
```

### Phase 1: Read Master Index — Identify Candidate Modules and Direct Specs

1. Read `{document tree path}/toc.md`.
2. Match the user's query description against the introduction of each module, submodule, and spec in the master index.
3. Each module in the master index has an index link (e.g., `[Module-A/toc.md](./module-a/toc.md)`). Extract relative paths and convert them to absolute paths using the path conversion rules.
4. Identify all reasonably relevant modules or direct specs (a query may match multiple — avoid matching too many, no more than 3 modules).
5. For specs directly hit in the master index (specs with descriptions and path links in the master index), extract relative paths, convert to absolute paths, and immediately append to `matched_specs` (`match_source` = `master-index-direct-hit`).
6. Output internal log (for tracking the search process, not the final user output):

```
[Explore] Query: "{query description}"
[Explore] Master index hit modules:
  - {module name}: index path {converted absolute path}, match reason: {explanation}
[Explore] Master index direct spec hits (added to matched_specs if any):
  - {converted absolute path}: {match reason}
```

7. If no matches are found in the master index, proceed directly to Phase 4 and output the "no results" message.

### Phase 2: Drill Down — From Module to Spec

For each candidate module identified in Phase 1, drill down sequentially. This phase has two parts: **module-level matching** and **submodule-level matching**.

#### 2A. Module-level Matching

1. Read the module's `toc.md` (using the absolute path converted in Phase 1).
2. The module index contains submodule index links (e.g., `[submodule-1/toc.md](./submodule-1/toc.md)`) and direct spec links (e.g., `[spec-zzz.md](./spec-zzz.md)`). Extract relative paths and convert to absolute paths.
3. Match the query description against submodule introductions and direct spec introductions.
4. For matched **submodules**, extract their index absolute paths, mark them for further drilling, and handle in 2B.
5. For matched **direct specs** (specs directly under the module), extract spec absolute paths and append to `matched_specs` (`match_source` = `module-direct-spec`).
6. Output internal log:

```
[Explore] Module {module name}
  Read module index: {path}
  Hit submodules (pending drill-down):
    - {submodule name}: index path {converted absolute path}, match reason: {explanation}
  Hit direct specs (added to matched_specs):
    - {converted absolute path}: {match reason}
```

#### 2B. Submodule-level Matching

For each submodule marked for further drilling in 2A, process sequentially:

1. Read the submodule's `toc.md` (using the absolute path converted in 2A).
2. The submodule index contains spec links (e.g., `[spec-xxx.md](./spec-xxx.md)`). Extract relative paths and convert to absolute paths.
3. Match the query description against spec introductions.
4. For matched specs, extract spec absolute paths and append to `matched_specs` (`match_source` = `submodule-spec`).
5. Output internal log:

```
[Explore] Submodule {submodule name}
  Read submodule index: {path}
  Hit specs (added to matched_specs):
    - {converted absolute path}: {match reason}
```

### Phase 3: Read Spec Documents + Source Code + Upstream/Downstream Trace + Relevance Verification

For every spec in the `matched_specs` list, process one by one:

1. Read the full spec document.
2. Extract source file paths and line number ranges from the spec document header.
3. Use the read tool to read the source code files directly associated with the spec. **[Mandatory] Must identify and prioritize the file that carries the core functionality** — do not arbitrarily pick peripheral files or enumerate all related files; determine which file contains the main implementation of the core logic. **[Mandatory] Source code must be read and output without skipping**; even if substantial omissions are needed, core code snippets must be preserved and must never be left empty.
   - **Source code length rule**: When the excerpt is ≤ 100 lines, it must be read in full without trimming; when > 100 lines, non-essential code may be appropriately omitted, but sufficient rich code detail must be retained, especially for core logic. Do not produce output dominated by comments with minimal actual code.
   - **[Mandatory] Omission annotation requirements** (for source code snippets): When omitting code, three conditions must all be met: ① write a comment at the omission point explaining which lines were omitted and the logic/function of the original code; ② on the line immediately below the comment, write `...` on its own line — do not put the ellipsis inside the comment; ③ irrelevant comments from the original source should also be omitted (deleted), keeping only the model-generated omission annotation. Example: `// (lines 25-80 omitted: schema validation logic)` followed by `...` on the next line.
   - **[Mandatory] Upstream callers** (for source code snippets): These are functional references; valuable core snippets should be preserved and not omitted.
4. **Upstream/downstream tracing**:
   - **Upstream**: Find which code calls the functions/interfaces in these source files (check imports, function call sites), and read key code snippets from callers
   - **Downstream**: Find which other modules/functions these source files depend on (check imports, callee sites), and read key code snippets from dependents
   - Record the traced upstream/downstream source files and include them in the output
5. **Relevance judgment**: Based on the spec document content (overview, feature details), actual source code, and upstream/downstream code, determine whether this spec is truly relevant to the user's query description. Criteria include:
   - Whether the spec's overview and feature description cover the queried business/feature
   - Whether the source code contains core logic, interfaces, or data structures related to the query
   - If relevant, keep the entry
   - If not relevant (merely a coincidental keyword match in the toc.md description), remove the entry from `matched_specs`
6. Output internal log:

```
[Verify] spec-{name}.md
  Judgment: relevant / not relevant
  Reason: {brief explanation of why relevant or not}
  Involved source files: {spec's direct source files + traced upstream/downstream source files}
```

### Phase 4: Output Results

Based on the verified `matched_specs` (at most top 4, sorted by relevance), present the final results to the user (no file writing needed).

**[Mandatory] Must read the reference document before outputting**. Before generating any results, must first read `references/OUTPUT-GUIDE.md`, and strictly follow its format specifications and self-check checklist. Do not skip.

Reference document path: `./references/OUTPUT-GUIDE.md` (relative to the openpowers-codebase-explorer skill directory).

Output structure overview (details in the reference document):

1. No-results message (or)
2. Query summary → Navigation path → Spec summary → Source code snippets
3. Each spec includes three source code sections: **direct source** + **upstream callers** + **downstream dependencies** — none may be left empty

#### 4.1 ~ 4.4 (Details in `references/OUTPUT-GUIDE.md`)

4.1 Query Summary, 4.2 Navigation Path, 4.3 Spec Summary, 4.4 Source Code Snippets — detailed format specifications are in the reference document `references/OUTPUT-GUIDE.md`, which must be read before outputting.

## Key Rules

1. **Depends on existing document tree**. This skill only reads the document tree already generated by openpowers-codebase-generator and does not generate new documents.
2. **Hierarchical navigation**. Strictly follow the master index → module → submodule → spec hierarchy for progressive lookup. Phase 1 only does module-level positioning; Phase 2 handles direct specs under modules (2A) and specs under submodules (2B) separately. Do not skip levels.
3. **Supports multiple results**. A single query may match multiple modules/submodules/specs, collecting at most the 4 most relevant specs for output.
4. **Fuzzy matching**. Query descriptions do not require exact matches; search for semantically related entries in the descriptions of toc.md files at each level.
5. **[Mandatory] Include source code**. Every matched spec must output its associated source code snippets alongside the spec document summary. Even if substantial omissions are needed, core code snippets must be preserved and must never be left empty.
6. **Source code length rule**. When the excerpt is ≤ 100 lines, it must be read/output in full without trimming; when > 100 lines, non-essential code may be appropriately omitted, but sufficient rich code detail must be retained, especially for core logic. Do not produce output dominated by comments with minimal actual code.
   **[Mandatory] When omitting code, the following three conditions must all be met** (all for source code snippet output): ① write a comment at the omission point explaining which lines were omitted and the logic/function of the original code; ② on the line immediately below the comment, write `...` on its own line — do not mix the ellipsis into the comment; ③ irrelevant comments from the original source should also be omitted (deleted), keeping only the model-generated omission annotation. Example: `// (lines 15-30 omitted: schema validation and default value population logic)\n...`
   **[Mandatory] Upstream/downstream caller source code snippets are functional references and should preserve valuable core snippets; do not omit them**.
